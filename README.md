# Daily Coding Practice

A personal daily coding practice system focused on building independent programming ability through deliberate practice, reflection, and accountability.

## Purpose

The goal of this repository is not to produce polished projects.

It is a training system designed to help me:

* Improve general programming and problem-solving
* Build practical React and JavaScript skills
* Prepare for eventual full-stack development and interviews
* Reduce dependence on AI for implementation
* Build a consistent daily coding habit
* Track progress through GitHub history and practice records

The core principle is:

> **AI may help me learn, but AI may not do my reps.**

## Session Model

The practice session currently uses an IPOF-style workflow:

```text
INPUT
  ↓
Read + prime + outline
  ↓
PROCESS
  ↓
Independent implementation + research
  ↓
OUTPUT
  ↓
Review
  ↓
FEEDBACK
  ↓
Personal reflection + AI review + session summary
```

The current session is approximately:

| Phase                     |      Time | Purpose                                                                                               |
| ------------------------- | --------: | ----------------------------------------------------------------------------------------------------- |
| Planning / Priming        |    ~5 min | Read the problem, outline the high-level details, and reason about responsibilities and relationships |
| Implementation / Research |   ~25 min | Solve independently, research documentation when necessary, and use the tutor when genuinely stuck    |
| Challenge Review          |   ~20 min | Review what happened, what worked, what failed, and what remains incomplete                           |
| Personal Reflection       |   ~15 min | Record what I learned, struggled with, figured out independently, and would change                    |
| AI Review / Summary       | ~5–10 min | Review the json generated by AI and modify if needed then copy paste it into practice.log.json        |

This means the current full workflow takes approximately **65–70 minutes**, while the core planning/implementation/research block is approximately **30 minutes**.

The implementation budget is intentionally adjustable.

The current implementation budget is approximately **25 minutes**. As my ability to implement independently stabilizes, that budget may gradually increase.

The purpose of the time limit is to create a consistent training constraint rather than guarantee that every challenge is finished.

An incomplete challenge is a valid practice session.

## AI Workflow

### 1. Generate the challenge

Zed is the primary coding environment and has access to the repository's practice history.

Use:

```text
/daily-challenge
```

The challenge generator uses `practice-log.json` as the primary source for deciding what to practice next.

It considers:

* Recent concepts
* Previous performance
* Acceptance criteria accomplished
* AI assistance used
* Hint levels used
* Recurring strengths
* Recurring weaknesses
* Recommended difficulty
* Challenge-type history
* Deliberate repetition
* Evidence of increasing independence
* Current implementation capacity

Difficulty is treated as a descriptive label rather than the primary measure of progression.

Past challenge implementations in `src/challenges/` may be inspected when additional context is useful.

The active `challenge.md` file is not historical curriculum data. It is a working scratchpad used to display the current challenge beside the code while implementing.

### 2. Independent implementation

Work on the challenge in Zed.

AI autocomplete and proactive AI assistance are disabled.

Normal developer research is allowed, including:

* Official documentation
* MDN
* React documentation
* Search engines
* Browser DevTools

The objective is to develop the ability to figure things out independently rather than memorize syntax.

The planning phase is deliberately used to practice problem decomposition and relational reasoning.

When appropriate, the learner should determine:

* Inputs
* Outputs
* Component/function responsibilities
* Data flow
* Relationships between concepts
* Important constraints

The challenge generator should provide the requirements without providing this decomposition.

### 3. Get help when stuck

A separate ChatGPT project is used as the tutoring environment.

The tutor follows a progressive hint ladder:

```text
Level 0 — Validation
Level 1 — Conceptual hint
Level 2 — Direction
Level 3 — Reasoning diagnosis
Level 4 — Pseudocode
Level 5 — Full solution
```

The lowest useful level should be used first.

Resource discovery is allowed. Asking for documentation, articles, specifications, or search queries does not count as receiving an implementation solution.

### 4. Review

After the implementation period, use the review skill.

The review focuses on:

* Correctness
* Reasoning
* Code quality
* Complexity
* React-specific concerns
* Testing
* What was done well
* What should be practiced again

The AI should diagnose rather than rewrite the solution.

### 5. Personal reflection

Before asking AI for the session summary, write my own reflection at the bottom of the current challenge file.

Each challenge uses:

```js
/*
==================================================
REFLECTION
==================================================

What I learned:
-

What I struggled with:
-

What I figured out without AI:
-

What I would do differently next time:
-

Important insight:
-
*/
```

The reflection is intentionally written by me rather than generated by AI.

The reflection captures both:

* Technical learning
* Meta-learning about how I think, reason, research, and solve problems

### 6. Record the session

Run:

```text
/session-summary
```

The skill outputs exactly one JSON object matching the schema used by `practice-log.json`.

The generated record should be reviewed and corrected manually before being added to the log.

The AI should not invent information that is unknown.

The structured log is treated as the curriculum memory, while the personal reflection in each challenge file remains the more detailed human learning record.

## Practice Tracking

`practice-log.json` is the structured source of truth for curriculum progression.

Each session records information such as:

```json
{
  "day": 1,
  "title": "Example Challenge",
  "type": "Feature",
  "difficulty": 2,
  "concepts": [],
  "planning_minutes": 5,
  "implementation_minutes": 25,
  "review_minutes": 20,
  "criteria_accomplished": 2,
  "criteria_total": 5,
  "completed": false,
  "ai_assistance_level": 2,
  "hint_levels_used": [1, 2],
  "strengths": [],
  "struggles": [],
  "learned": [],
  "reinforce": [],
  "recommended_difficulty": "same",
  "recurring_weakness": null,
  "recurring_strength": null
}
```

### Acceptance Criteria

Progress is measured using:

```text
criteria_accomplished / criteria_total
```

rather than treating completion as a simple pass/fail measure.

`criteria_total` contains only required acceptance criteria.

Optional stretch goals do not count.

`completed` is `true` only when all required acceptance criteria are satisfied.

The purpose of this measurement is to describe performance, not to determine whether the day "counted."

### AI Assistance

`ai_assistance_level` represents the highest hint level actually used.

`hint_levels_used` records the hint levels actually used during the session.

Resource discovery does not increase the hint level.

For example:

```text
ai_assistance_level: 2
hint_levels_used: [1, 2]
```

The purpose of this metric is to track increasing independence over time, not to judge a session as good or bad.

## Repository Structure

Challenges are kept chronological.

Simple challenges may remain as individual files:

```text
src/
└── challenges/
    ├── day-001.jsx
    ├── day-002.jsx
    └── day-003.jsx
```

When a challenge naturally requires multiple files, it may use its own directory:

```text
src/
└── challenges/
    └── day-004/
        ├── day004.jsx
        ├── components/
        └── context/
```

The repository does not organize challenges into folders such as `react/`, `debugging/`, or `refactoring/`.

Challenge type is recorded as metadata instead.

Examples:

```text
Feature
Problem Solving
Debugging
Refactoring
Async/Data Handling
Testing
```

The active challenge is placed in:

```text
challenge.md
```

This is a temporary/current-session scratchpad designed to make the challenge easy to view alongside the implementation in a split-screen editor.

Historical challenge information lives with the corresponding challenge file.

Structured progression information lives in:

```text
practice-log.json
```

## GitHub Accountability

Each practice session should result in a Git commit and push.

Example:

```text
day 001: interactive counter component
day 002: shopping cart quantity adjuster
day 003: todo list with filter
day 004: broken theme toggle debugging
```

Incomplete challenges are still committed.

GitHub serves primarily as:

* Accountability
* A visible practice history
* A record of consistency
* A record of technical progression

The repository is not primarily a collection of portfolio-ready projects.

A GitHub push may also trigger an automated Discord notification for additional accountability.

## Separate Personal Journal

The coding practice system is intentionally separate from my broader personal writing system.

My Obsidian vault is used for general daily writing, productivity, reflection, and broader life context.

This repository is specifically for:

* Coding practice
* Technical learning
* Programming reflection
* Curriculum progression
* Accountability through Git

The two systems may reference each other when useful, but they do not need to be integrated.

## Long-Term Direction

The practice system may eventually evolve into a personal coding-learning application.

A possible future direction is to use the accumulated practice history, reflections, and code as a retrieval source for a personal coding coach.

That may eventually involve RAG or another retrieval mechanism.

That work is intentionally deferred.

The immediate priority is to accumulate high-quality practice data and determine what the system actually needs before building additional infrastructure.

## Current Principle

The system is allowed to evolve as evidence accumulates.

New schema fields, automation, tooling, and infrastructure should be introduced when repeated practice demonstrates a genuine need for them.

The current priority remains:

> **Show up, think, implement, research, reflect, record, and commit.**
